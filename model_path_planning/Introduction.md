# 无人机任务级路径规划模型入门

## 1. 它到底在规划什么

这个项目不是给无人机规划“每一秒飞向哪个姿态”的飞控轨迹，也不是做避障地图。它做的是更上层的任务安排：

> 警报发生后，哪架无人机去哪些风险点、按什么顺序投放、什么时候回站补货，才能让高风险点尽快获得治理。

在系统闭环中的位置是：

```text
检测节点报警
      ↓
上游浓度/水流/降解模型给出任务点、剂量和时滞
      ↓
本项目：分配无人机 + 生成访问顺序 + 必要时滚动重规划
      ↓
下层飞控执行每一段飞行
```

因此它关注的是“任务级路径”，不负责绕障、姿态控制或精确悬停。

## 2. 把现实问题翻译成一个 `Instance`

代码用 `code/env.py` 中的 `Instance` 描述一轮规划。首次阅读时，可以把它理解成一张包含以下信息的任务表：

| 信息 | 含义 |
|---|---|
| 节点坐标 | 停机坪和风险点在哪里 |
| `risk` | 每个风险点有多紧急，越大越应优先 |
| `demand` | 该点需要投放几包菌剂，热点可以大于 1 |
| `tw_end` | 软截止时间，迟到会增加代价但不一定直接作废 |
| `T[k,i,j]` | 第 k 架机从 i 到 j 的飞行时间 |
| `drone_cap` | 每架机一次能带多少包 |
| `drone_energy` | 可用续航，并且必须留出返航能量 |
| `drone_depot` | 每架机属于哪个停机坪 |
| `eff_lag` | v3.0 中从投放到治理真正生效的额外时滞 |

模型输出是每架无人机的节点序列，例如：

```text
无人机 0：停机坪 → 任务 10 → 任务 8 → 回站
无人机 1：停机坪 → 任务 5 → 任务 9 → 任务 4
```

## 3. 它优化的不是“总飞行距离”

项目的统一目标函数是：

```text
目标 = Σ 风险权重 × 任务完成时间
     + 软时间窗迟到惩罚
     + 最晚收尾时间惩罚
     + 未服务任务惩罚
     + （必要时）不可行解重罚
```

这意味着：高风险点即使距离稍远，也可能比低风险点更早安排。代码中的 `env.objective()` 是所有方法共用的评分器，贪心、OR-Tools、强化学习生成的路线都必须交给它回放，这样比较才公平。

对于每架无人机，评分器会逐段模拟：飞行耗时、投放悬停时间、载荷消耗、能量消耗、回站补货和返航。一个任务只有在完成所需的最后一次投放后才算完成；能量检查还会确认从当前位置到任务点后仍能返回所属停机坪。

## 4. 风怎样进入路径规划

`code/scenario.py` 读取 OSM 东湖水域、Open-Meteo 风场和模拟检测设备位置，构造东湖场景。风不会简单地加到一个总耗时上，而是改变每一条边的飞行时间：

```text
顺风边：地速更快
逆风边：地速更慢
所以 T[i,j] 通常不等于 T[j,i]
```

`wind_time_matrix()` 用风的平行分量修正空速，并加入航线安全系数和悬停时间。这样“去程顺风、回程逆风”的非对称成本可以传给调度器。

默认东湖场景包含 3 个停机坪、3 架异构无人机和若干风险任务点；无人机的速度、载荷和续航不同。高风险点的软窗更紧，风险权重来自检测/浓度场景的模拟值。

## 5. 机器学习模型怎样生成路线

### 5.1 编码器：让网络先看懂整张任务图

`code/model.py` 先把每个节点的 6 维特征投影到 128 维：

- 归一化坐标；
- 需求包数；
- 风险权重；
- 软截止时间；
- 预留/边信息特征。

之后通过 3 层、8 头、隐藏维度 128 的 Transformer 自注意力，得到每个节点的嵌入。注意力适合这里的原因是：任意节点之间都可能直飞，且一架机去某个点会影响其他无人机的选择，需要全局看节点之间的竞争关系。

### 5.2 解码器：每一步联合选择 `(无人机 k, 节点 j)`

它不是“先排完无人机 0，再排无人机 1”。每一步都在所有 `(k,j)` 对里选择一个动作：

1. 读取整张图的平均嵌入；
2. 读取每架机当前所在节点；
3. 读取该机剩余载荷、剩余电量和自己的时间；
4. 为每架机对所有节点计算注意力分数；
5. 联合采样一个“哪架机去哪个点”的动作。

这种写法与现实中的多机并行执行更一致。

### 5.3 约束掩码：不让网络选择明显不可能的动作

网络本身不懂“电量够不够返航”，因此 `train.py` 在 softmax 前生成布尔掩码，把不可行动作的分数设为极小值。主要规则包括：

- 任务还没有完成需求量；
- 无人机还有投放包；
- 去任务点后仍有足够能量返航；
- 不超过规划时域；
- 回站只能回所属停机坪，并且确实需要补货/充电；
- 不能无意义地停在当前位置。

训练结束后，`env.objective_times()` 会再次进行能量和服务审计。掩码是第一道防线，评分器复核是第二道防线。

## 6. 怎么训练

这是一个组合优化问题，没有“正确路线标签”可直接监督学习。项目使用 POMO-lite + REINFORCE：

1. 每次随机生成一批东湖任务实例；
2. 对同一个实例采样 `S=8` 条路线；
3. 用这 8 条路线的平均目标作为基线；
4. 比平均值更好的路线提高概率，更差的路线降低概率；
5. 反复训练策略网络。

推理时再对同一个实例采样 32 条左右，交给统一评分器取最优路线。这样单条路线的随机性不会直接决定最终方案。

V2.7 还加入了两类增强：

- `--use-edge`：把平均到达成本、离开成本、风致非对称度等边信息聚合成节点特征；
- `--tanh-prior`：用边成本作为解码先验，避免网络完全忽视飞行代价。

## 7. 基线、局部搜索与动态重规划

除了 RL，项目还实现了：

- `greedy_solve()`：每次选当前可行且风险加权较低的下一步；
- `ortools_solve()`：把问题近似成 OR-Tools 的 MDVRPTW，再用统一评分器重评；
- 局部搜索：在线路内做 2-opt，或把任务从一架机搬到另一架机；
- `replan_demo.py`：在 `t=0、20、45、70` 分批注入新警报，比较固定计划、RL 事件重规划和贪心重规划。

动态重规划的过程是：先把无人机推进到新事件时刻，保留它们的当前位置、载荷和电量；再把未完成任务组成一个新 `Instance`，重新求一份路线。代码把“当前无人机位置”临时当成新的停机坪，使同一个策略网络可以继续工作。

## 8. 与水流和降解模型的衔接

`code/flow_tasks.py` 是 v3.0 的接口适配层。它尝试把上游模块的结果转成路径任务：

- 从二维水流优化结果中选择高分且相互间隔足够的投放点；
- 根据初始浓度、治理时限和剂量-时间关系计算每个点需要几包；
- 把菌团漂移时间和降解达标时间合成 `eff_lag`；
- 让路径规划优化“治理生效时间”，而不只是“无人机到达时间”。

当前这部分仍使用演示标定常数（例如 1 包对应的剂量、`C_REQ` 和基准速率），要等上游真实标定数据接入后才能作为正式决策接口。

## 9. 当前实验结论与边界

V2.7 在 16 个未见过的东湖测试场景上，RL-B 的风险加权完成时间约为 15.34 min，综合目标约 16.27；RL-B + 局部搜索约 16.04。单次推理约 0.06 s，明显快于 5 s 预算的 OR-Tools 基线，适合高频重规划。

强风压力测试显示，风感知规划的价值首先体现在**可行性**：欧氏距离规划可能产生无法安全返航的路线，而风感知路线仍能通过能量审计。微风下边特征的收益较小，强风下更明显。

需要同时记住以下限制：

- 公共 VRP 基准上的 OOD 泛化明显差于东湖分布，RL 不能被当成通用 VRP 求解器；
- OR-Tools 在部分 OOD 实例上会失败并回退到贪心，比较时必须看状态字段；
- 重规划是否优于固定计划取决于新警报的风险和到达时机，不能把某一次演示的改善百分比当成普遍规律；
- 模型只做任务级路线，不包含真实障碍、禁飞区、通信中断和飞控误差。

## 10. 推荐阅读和复现

建议按以下顺序：

1. `README.md`：版本、命令和实验产物；
2. `report/03_无人机任务级路径规划模型架构报告.md`：正式定义和结果；
3. `report/04_模型教学讲解.md`：逐步走查一次推理；
4. `code/env.py`：评分器；
5. `code/scenario.py`：东湖场景；
6. `code/model.py`、`code/train.py`：网络和训练；
7. `code/replan_demo.py`、`code/flow_tasks.py`：动态和跨模块接口。

典型命令：

```powershell
cd model_path_planning/code
python scenario.py
python train.py --steps 1200 --d 128 --use-edge --tanh-prior --out outB
python evaluate.py --ckpt outB/ckpt.pt
python replan_demo.py --ckpt outB/ckpt.pt
python flow_tasks.py
```
