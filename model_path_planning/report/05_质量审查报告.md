## 0. 总体结论

**架构设计与文档质量：优秀（iGEM 标准下接近模范）；实验实现与结论可靠性：不合格，需要返工。**

这个模块在设计层面做对了很多事：问题形式化清晰（MD-MUAV-VRPTWP-E）、"统一评分器"保证了跨方法可比性、能量含返航余量的掩码设计、用真实东湖 OSM+风场数据训练而非纯随机分布、OOD 测试主动暴露泛化差距并诚实写入报告、26 轮审查日志真实可读且可追溯（RV-01 至 RV-26 逐条有"发现→决策→影响"）。这些都应肯定。

但**审查发现 5 个可实测复现的实现缺陷**，其中两个直接动摇报告的核心结论：

1. **局部搜索模块是空操作**（实测：16 个测试场景上对输入的改进为 0.0%，修复该缺陷后贪心+局部搜索从 37.77 → 16.87，与 RL 的 16.69 仅差 1%，且风险加权完成时间指标反超 RL）。报告 §5.2 的"RL 比贪心+局部搜索优 56%"主结论因此失真，§5.2 对"纯启发式初解卡在深局部最小"的机理归因是错的。
2. **OOD 表中"OR-Tools"列实际是贪心结果**（实测：9/9 个实例上 OR-Tools 求解失败、静默回退贪心，两列逐行相同，报告未披露且只展示了 6/9 行）。

另有多处"报告结论 ↔ 代码现实"不符：λ 敏感性消融未实现却作为论据引用；训练默认超参（d=96）与正式模型（d=128）不一致导致复现命令失真；训练时多机共享单一时钟扭曲时间掩码；多访问任务的完成时刻统计量错误污染 OOD 全部数值；数据侧 547 MB 损坏文件被标注为"已验证完整"、约 48 MB 逐字节重复目录、2 GB 数据完全未纳入 git 管理。

**一句话评价**：这是一份"设计 95 分、实现 60 分、诚实度 85 分（重要结论旁都有自我披露，但披露未覆盖真正的硬伤）"的工作。好在所有缺陷都是**可修复的**，修复后架构依然成立。

## 2. 致命缺陷详解（含复现证据）

### F1：局部搜索是空操作（影响 §5.2 主结论）

**代码**（`evaluate.py:17-49`，简化后）：

```python
def local_search(inst, routes, tsp_iters=600, seed=0):
    rts = copy.deepcopy(routes)
    best, _ = objective(inst, rts)
    for it in range(tsp_iters):
        # ... 对 rts 做 2-opt / relocate 扰动 ...
        o, _ = objective(inst, rts)
        if o < best - 1e-9:
            best = o
        else:
            rts = copy.deepcopy(routes)      # ← BUG：重置回"最初的输入"
            best, _ = objective(inst, rts)
    return rts, best
```

扰动被拒绝时，`rts` 被重置为函数入参 `routes`（初始解），而不是"上一次被接受的最好解"。任何一次拒绝都会抹掉此前累计的全部改进。实测：

| 度量 | 报告值（表 1） | 实测（16 场景，seed 9000–9015） |
|---|---|---|
| 贪心 obj | 37.93 | 37.93 |
| 贪心+LS obj（as shipped） | 37.77 | 37.77（**对输入的改进为 0.0%**） |
| 贪心+LS obj（修复该行后） | — | **16.87**（改进 55.5%） |
| RL 采样32 obj | 16.60 | 16.69 |
| 修复后贪心+LS 的 rwt | — | **15.60（反超 RL 的 15.83）** |

**结论改写**：报告 §5.2 声称"RL 比贪心+LS 优 55.8%、贪心+LS 几乎无提升说明启发式初解卡在深局部最小"——**机理归因完全错误**。真实情况是：一个实现正确的随机 2-opt/relocate 爬山（无模型、零训练成本、同样 0.04 s）在目标值上与 RL 持平（16.87 vs 16.69，差 1.0%），在风险加权完成时间上反超。"RL 大幅优于一切启发式"的核心卖点不成立。RL 的价值主张需要重新论证（见 §6）。

### F2：OOD 表"OR-Tools"列是贪心（影响 §5.5）

`solvers.py:102-103`：`sol is None → return greedy_solve(inst, gamma)`，无任何提示。实测 9/9 个 OOD 实例：

```
VRPTW_C1_10_1:  greedy 892.0  ortools 892.0   ← 逐行相同
...（9/9 全部相同）
```

报告表 4 的 OR-Tools 数字与贪心完全相同，却作为"OR-Tools 在 OOD 上稳健、RL 退化"的证据呈现。**讽刺的是，修正后的结论方向反而更强**：真正的 OR-Tools 在这些实例上**根本求不出解**，说明"任意转换的公共基准"连求解器都扛不住——这恰恰支持报告的 sim-to-real 论点。但数据必须重跑重写。另外表 4 只展示 6 行，`out/ood_results.json` 实际有 9 行（被省略的 3 行 RL 也全败，无选择性删减之嫌，但属未披露）。

### F3：训练时多机共享单一时钟

`train.py:80`：`tnow = torch.zeros(B2)`（形状 B2，**不是 B2×m**），三架机的 leg 时间全部累加进同一标量。实测一个典型轨迹：三架机真实结束时刻为 [12.98, 11.55, 13.58] min，rollout 时钟却记到 38.11 min（=三者之和，约真实 makespan 的 2.8 倍）。后果：策略上下文里的"时间"被放大、`time_ok` 掩码过早收紧。当前 180 min 时域内基本不触发（所以最终评分不受影响——`env` 逐机重算），但报告 §3.3 的"每架机时间/电量/载荷独立推进"对时间维度不成立，且任何更大的场景会直接受影响。

## 6. 对"模型价值"的重新评估（修复缺陷后的真实图景）

按 F1 修复后的数字重新看 §5.2：

| 方法 | obj（16 场景均值） | 求解时间 | 训练成本 |
|---|---|---|---|
| 贪心 + 修复版局部搜索 | 16.87 | 0.04 s | **零** |
| RL 采样32（本模型） | 16.69 | 0.04 s | 24 min CPU + 生成器工程 |
| RL 采样32 + 修复版局部搜索 | 预期 ≤16.6（略优） | ~0.08 s | 同上 |

在**当前规模和当前分布**下，"学习"部分的边际收益接近零——简单构造 + 正确实现的爬山就能打平。这不是说架构路线错了，而是说**报告目前的证据不足以支撑"必须用学习式方法"的论证**。RL 路线的真实价值主张应转移到以下三点，并补做相应实验：

1. **采样推理在毫秒级预算内天然给出 32 个可并行评估的候选解**（爬山只有一个）——重规划场景中可做滚动时域多假设评估；
2. **规模外推**：风险点 50–200 时，爬山每步需要 O(n²) 次评分、迭代预算爆炸，而 RL 前向仍是固定开销——需要做"n=50/100 时贪心+LS vs RL"的对照实验证明；
3. **状态依赖决策**（"包快没了是否回站"这类前瞻）爬山无法直接表达——需要构造"回站决策显著影响最优解"的专门场景来验证策略确实学到了它。

**在补上这些证据之前，模型应定位为"原型与基础设施"，而非"已证优的求解器"。**
