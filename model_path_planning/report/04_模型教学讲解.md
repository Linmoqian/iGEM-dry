## 1. 先建立直觉：这个模型在系统里干什么

整个 iGEM 项目是一条闭环：

```
漂浮检测节点(工程菌+荧光传感) 持续测量水体 MC-LR
        │ 浓度 ≥ 1 μg/L 预警阈值
        ▼
中控系统收到"警报"：某处水域有毒素风险，需要派无人机去投放降解菌
        │
        ▼
【本模型】决定：哪几架无人机出动？谁先去哪个点？按什么顺序？
          载荷用完/电量不够时谁回停机坪补给？新的警报来了怎么改计划？
        │ 输出 = 每架无人机的"访问序列"（先 A 后 B，中途回站补货再飞 C）
        ▼
无人机执行（轨迹级避障、悬停投放由下层飞控负责——不在本模型范围）
```

一句话：**本模型是"任务级"调度器，回答"谁、何时、去哪、什么顺序"，不回答"怎么飞出一条无碰撞轨迹"。**

它要处理的三个核心困难：

1. **优先级不平等**：同样是 10 个报警点，浓度 5 μg/L 的点应该比 0.5 μg/L 的点更早被照顾。"最快投放"不是"最快飞完"，而是"风险加权意义上最快"。
2. **物理约束真实存在**：无人机载荷只有 4~6 包投放剂、电量只够飞约半小时、逆风飞比顺风飞慢——忽略这些，规划出来的航线执行不了。
3. **世界是动态的**：警报不是一次性给全的，t=0 报 5 个点、t=20 分钟又报 2 个点。计划必须能"滚动重排"。

## 2. 问题形式化：把"最快投放"翻译成数学

### 2.1 决策变量与输入

每轮规划时已知（`env.py` 里的 `Instance` 数据类）：

| 符号 | 含义 | 例子（真实场景见 §9） |
|---|---|---|
| 节点集合 | n_dep 个停机坪 + n_task 个风险点 | 3 停机坪 + 10 风险点 = 13 节点 |
| `xy` | 各节点坐标（km，平面近似投影） | 东湖湖面及岸线 |
| `T[k,i,j]` | **第 k 架机**从 i 飞到 j 的时间（分钟，**风修正、非对称**） | T[3,7]=1.45 ≠ T[7,3]=1.73 |
| `demand[j]` | 任务 j 需要的投放包数 | 大热点 >1（当前训练场景均为 1） |
| `risk[j]` | 风险权重 w_j ∈ (0,1]，由浓度映射 | w = min(浓度,6)/6 |
| `tw_end[j]` | 软截止窗：w 越高窗越紧 | l_j = 25 + 45·(1−w_j) 分钟 |
| 机队参数 | 每机载荷上限、续航、巡航速度、所属停机坪 | 3 机：Q=4/4/6 包，E=28/28/34 min，v=15/15/13 m/s |

**输出**（一个"解"）：每架无人机的访问序列 `routes[k]`，序列里允许出现停机坪编号，表示"中途回站补货"。例如：

```python
routes = [[10, 8, 7], [12, 3, 6], [5, 9, 4, 11]]
# 无人机0：出库 → 任务10 → 任务8 → 任务7
# 无人机1：出库 → 任务12 → 任务3 → 任务6
# 无人机2：出库 → 任务5 → 任务9 → 任务4 → 任务11
```

### 2.2 目标函数：风险加权投放时间

模型优化的不是"总路程"，而是（`env.objective()`）：

```text
Objective = Σ_j w_j · t_j                      # 主目标：每个点的完成时刻按风险加权
          + λ · Σ_j w_j · max(0, t_j − l_j)     # 软窗迟到惩罚（λ=2.0）
          + μ · makespan                       # 最晚收尾惩罚（μ=0.05，运维考虑）
          + ν · Σ_j w_j · [未服务]              # 未服务惩罚（ν=50，防止放弃任务）
```

为什么第一项才是"最快投放"的正确表达？设想两个任务 A（w=0.9，高危）和 B（w=0.1，低危）。"先飞 B 再飞 A"比"先 A 后 B"总路程可能一样，但 Σw·t 会大很多——因为它给高危点的迟到记了 9 倍的账。**这个目标让"快"和"先救高危"自动一致。**

为什么是软窗而不是硬截止？MC-LR 风险是**连续演化**的（湿实验显示浓度随时间爬升、2 小时左右达峰），不存在"过了某时刻任务作废"的物理边界。软窗 + 线性迟到惩罚与"越晚投放、累积风险越大"的语义一致（审查轮 RV-06）。

### 2.3 约束（五类，对应五个掩码，见 §6）

| 约束 | 含义 | 为什么需要 |
|---|---|---|
| 需求 | 任务 j 被投放满 demand[j] 次才完成 | 大热点要多投几包 |
| 载荷 | 每机一次出航最多带 Q_k 包，空了必须回站 | 多航次 multi-trip |
| **能量（含返航）** | 任意时刻剩余电量 ≥ 飞到下一目标 + 从目标返回本机停机坪 | 保证任何时刻可安全返航 |
| 时间 | 当前时刻 + 飞行时间 ≤ 计划时域 H=180 min | 计划有界 |
| 停机坪 | 只能回自己所属停机坪，且仅在"载荷空或电量低"时回 | 业务规则 |

能量约束是整套设计里最值得记住的一条：**只检查"这一腿够不够飞"会产生飞到一半没电的死局，必须检查"这一腿 + 返航"都够**（RV-09）。代码里的对应物是训练掩码里的 `en_ok_task = en_rem − T_leg − T_ret ≥ 0`。

## 3. 场景层：东湖场景生成器 `scenario.py`

### 3.1 为什么要有"场景生成器"这个模块

神经网络路线规划器（NCO，Neural Combinatorial Optimization）的一个著名陷阱是 **sim-to-real 差距**：在"均匀随机撒点"上训练出的策略，放到真实分布上会退化。本项目的对策是——**手里有真实信号，就用真实信号合成训练分布**（RV-12）：

| 真实信号 | 来源 | 用途 |
|---|---|---|
| 东湖水系多边形（920 条 way，17,394 个点） | OpenStreetMap Overpass API | 风险点/停机坪落在真实湖形内 |
| 2024 年 6–9 月逐小时风场（2928 小时） | Open-Meteo 历史存档 | 每次采样真实小时的风速/风向 |
| 14 个检测装置的坐标与浓度先验 | 项目 web 前端 `demoReadings.ts` | 风险点空间分布与浓度-风险映射 |

### 3.2 逐步骤拆解 `build_eastlake()`

1. **取湖形**：`load_osm_water()` 解析 `osm_eastlake_water.json`，取节点最多的多边形 = 东湖主水面。
2. **撒风险点**：在监测包围盒（30.545–30.585°N, 114.360–114.405°E）内均匀采样 n_task 个点；浓度按 **30% 高（2–6 μg/L）/ 40% 中（1–2）/ 30% 低（0–1）** 的混合分布抽取——这是从 14 个装置的真实浓度分布观察来的先验。
3. **映射风险与窗口**：
   ```python
   p = min(conc / 6.0, 1.0)          # 风险权重 w
   tw_end = 25 + 45 * (1 - p)        # 高风险 → 窄窗口
   ```
   浓度 5 μg/L → w=0.83、窗 32.6 min；浓度 0.5 → w=0.08、窗 66.3 min。
4. **坐标投影**：经纬度 → 以湖心 (30.5667, 114.3833) 为原点的等距投影（km）。
5. **风修正时间矩阵**（核心物理，见下）。
6. **组装机队**：3 架异构机，参数见 §2.1 表。

### 3.3 风如何进入模型：`wind_time_matrix()`

风向/风速来自 Open-Meteo（2024 年 6–9 月逐小时）。气象学的"风向"指**来风方向**，先转成风矢量：

```python
u = -wspd * sin(rad);  v = -wspd * cos(rad)   # 来风向 → 吹向
```

然后对每对 (i, j)：把风矢量分解为**沿航线分量 v_par** 和**垂直分量**，用速度三角形近似地速：

```python
v_par = wind · 航线单位向量                      # 顺风为正
v_g   = sqrt(v_air² − v_vert²) + v_par          # 垂直风分量只做减法（漂移损耗）
T[i,j] = d · safety / v_g                       # safety=1.25 航线系数
```

关键性质：**T[i,j] ≠ T[j,i]**——顺风飞过去快、逆风飞回来慢。§9 的真实例子中 T[3,7]=1.45 min 而 T[7,3]=1.73 min，差值 0.28 min 就是风的不对称性。图 4 直接可视化了这个非对称矩阵。

> 注意：这一层只把风写进"飞行时间矩阵"，而策略网络的编码器（§5）当前**并不直接读取 T 矩阵**——风的影响目前通过能量/返航掩码间接进入决策。报告 §5.3 的消融实验发现策略对风"不敏感"（风感知 vs 欧氏仅差 ~1%），并据此把"边特征融入编码器（RRNCO 式 GNN-ANE）"列为 V2.7 的头号未做项。这是报告最诚实也最值得点赞的部分：**它实验性地证明了自己的当前架构哪里不够**。

## 4. 统一评分器 `env.py`：所有方法共用的一把尺子

### 4.1 为什么单独做这个模块

对比实验最常见的人为偏差是"各方法各评各的"。本项目规定：**贪心、OR-Tools、RL 三方解出来的 `routes` 全部丢进同一个 `env.objective(inst, routes)` 打分**（RV-05/RV-18）。这把尺子长什么样，前面 §2.2 已给出。

### 4.2 仿真器如何"播放"一条路线：`objective_times()`

```python
for 每架机 k（独立推进）:
    t = 0;  energy = E_k;  cur = 所属停机坪
    for 序列中的下一个节点 nxt:
        if nxt == 停机坪:              # 回站补货
            t += T[k,cur,depot] + refill_time(12min)
            energy = E_k               # 补满
        else:                          # 访问任务
            leg = T[k,cur,nxt]
            t += leg + hover_time(0.13min)   # 悬停投放
            energy -= leg
            if energy < T[k,nxt,depot]: feasible = False   # 返航审计
            visit_count[nxt] += 1
            if visit_count[nxt] >= demand[nxt]: t_complete[nxt] = t   # 完成时刻
        cur = nxt
```

要点：

- **每架机的时间线独立**（与真实世界"三架机同时飞"一致），makespan = max(各机结束时刻)。
- 完成时刻 t_j 记在"该任务被投放满 demand 次的**那次**访问"上。
- 能量约束在仿真器里**再审计一遍**（双保险：掩码保证 + 仿真器复核，RV-14）。

## 5. 策略网络 `model.py`：注意力编码器 + 多智能体指针解码器

### 5.1 为什么是 Transformer 注意力（而不是别的）

| 候选 | 为什么不选 | 选型轮次 |
|---|---|---|
| 逐点前馈网络 | 只能看"每个点自己"，看不到"点之间的耦合"——而本问题里一架机的选择会影响其它机的可达性 | RV-07 |
| 图神经网络 | 需要人工构造邻接；本问题是**完全图**（任意两点可飞），注意力天然就是完全图上的消息传递 | RV-07 |
| Transformer 编码器 | 全局耦合 + 在 VRP 上被 AM/POMO 反复验证 + 实现成熟 | ✅ |

灵感来源（文献 1.1/1.2）：Kool et al. 2019 的 Attention Model 证明"端到端学路由"可行；Kwon et al. 2020 的 POMO 证明"多起点采样共享基线"能大幅提升解质量。规模上：节点 10–50，注意力 O(n²) 完全无压力。

### 5.2 编码器：节点 → 嵌入 h_j

每个节点 j 的 6 维原始特征：

```
[0:2] 归一化坐标 x,y（z-score）
[2]   需求 / DEMAND_MAX
[3]   风险权重 w
[4]   软窗截止 / HORIZON
[5]   占位特征（恒为 0，当前未使用）
```

流程：`输入投影 (Linear 6→128) + 类型嵌入 (停机坪/任务) → 3 层 Transformer 编码器（d=128, H=8 头, FF=512）→ h_j (128 维)`。

编码器一次前向即可得到全部节点的嵌入，训练时**同一个嵌入被 8 条采样轨迹复用**（省算力）。注意编码器是置换等变的、输入不含 T 矩阵——这也是 §3.3 提到的"风不敏感"的结构根源。

### 5.3 解码器：每步联合选择 (无人机 k, 目标 j)

这是整个模型最具特色的设计（RV-08）。**不是**"先给 1 号机排完路线再排 2 号机"（那样把机间竞争变成了人为的先后顺序，多机场景显著次优），而是**每一步在所有 m×n 个 (机,点) 对里选一个动作**：

```text
上下文 ctx_k = ctx_proj( [图均值嵌入 h_bar + 当前所在节点嵌入 h_{cur_k}  ← "我在哪、图里有什么"
                          + 动态特征 (剩余载荷, 剩余电量, 时间) ]  )    ← "我什么状态"
q_k = q_proj(ctx_k)                       # 每架机一个"查询"
logits[k, j] = (q_k · h_j) / √d           # 指向所有节点的分数（点积注意力）
logits = logits.masked_fill(infeasible, -1e9)   # 不可行动作置 −∞（§6）
然后 log_softmax 归一化 → 采样一个 (k,j)
```

- **图均值嵌入**：让每架机"看到全局"（哪些点还剩、整体图景）——全局耦合的来源。
- **当前节点嵌入**：指针机制，让解码器知道这架机现在在哪。
- **动态特征（载荷/电量/时间）**：解码器循环的每一步都重新计算，所以策略能表达"我的包快没了 → 去回站"这类状态依赖决策。
- **动作空间 m×n**：3×13=39 个选项，每步选一个；最多约 2·Σdemand+补货次 步终止。

### 5.4 和标准 Attention Model 的关系

标准 AM 是"单旅行商 + 指针选择下一个城市"；本模型是它的多机扩展：**多智能体联合指针解码**。每步选的是"哪个智能体动 + 去哪"，等价于把 m 个正在并行执行的任务序列交错地构造出来——这与现实中三架无人机同时飞行的执行语义同构。

## 6. 约束掩码：把物理规则塞进神经网络

神经网络不知道什么是"电量不够返航"。办法：**给每个 (k,j) 动作算一个布尔"可行"矩阵，不可行的在 softmax 前置 −∞，从概率上杜绝**（RV-09）：

```python
# 目标 j 是任务时，以下任一不满足则屏蔽：
served_ok   = 该点已投放数 < 需求数                 # 需求没做完才可再去
load_ok     = 本机剩余载荷 ≥ 1                       # 有包可投
en_ok_task  = 剩电 − 去程 − 返航 ≥ 0                  # 能量安全（含返航余量！）
time_ok     = 当前时刻 + 去程 ≤ 180                   # 计划时域

# 目标 j 是停机坪时（回站动作），必须全部满足：
是本机所属停机坪 & 需要补货(载荷空 或 电量<50%) & 当前不在该停机坪 & 剩电够飞回去
```

掩码的意义不只是"不出错"：它让策略网络**不需要自己学会物理定律**，学到的注意力分布天然落在可行域内。这也是报告 §8.1 所说"每个掩码对应一条可被审计的物理/业务约束"的含义。

> ⚠️ 一个被审查发现的真 bug 就藏在这里（见 §12-②）：**时间掩码用的 `time_now` 是"所有机共享的单一时钟"**，三架机的飞行时间被累加到同一个数上，而非各自独立。真实评分器（§4）不受影响（它逐机重算），但训练时策略看到的"时间"信号是被放大的。这恰好是一个教学案例：**掩码的正确性 = 状态的正确性**，状态错，掩码就错。

## 7. 训练层 `train.py`：POMO-lite REINFORCE

### 7.1 强化学习视角

- **状态**：场景 + 已服务情况 + 各机(位置/载荷/电量/时间)。
- **动作**：(k, j)，受掩码约束。
- **奖励**：只在序列构造完后给一次 = −Objective（目标越小越好 → 奖励越大越好）。**没有中间奖励**（RV-13：终局统一评分，避免传递奖励的塑形噪声）。

### 7.2 REINFORCE 与 POMO-lite 的差别

REINFORCE 的经典问题是**方差大**：单条轨迹的得分波动会把梯度方向淹没。POMO 的解法是——**对同一个实例采样 S=8 条轨迹，用"这 8 条的均值"作基线**：

```python
objs = objs.view(B, S)              # 每个实例 8 条采样
baseline = objs.mean(dim=1)         # 同实例共享基线
adv = baseline - objs               # 比均值好的轨迹 → 正优势 → 增大其概率
loss = -(adv.detach() * logps).mean()
```

- "lite"在哪？标准 POMO 用**不同起点**保证轨迹多样性，这里用"同策略采样 8 次"近似。报告在 §3.7 明确承认这一简化（RV-11）。
- 为什么合适？推理时本来就要"多采样取最优"（§8.3），训练与推理结构天然同构。
- 为什么不用 PPO/带价值网络？小规模构造任务上，共享基线已把方差压到足够低，第二套价值网络是纯成本。

### 7.3 训练超参（与 `out/ckpt.pt` 一致）

| 项 | 值 |
|---|---|
| 网络 | d=128, L=3, H=8, FF=512 |
| 数据 | 每步随机生成 16 个东湖实例（n_task=10），风况从 8 个真实小时随机抽 |
| 采样 | S=8 / 实例 |
| 优化 | Adam lr=1e-4，梯度裁剪 1.0，1200 步，CPU 约 24 分钟 |
| 验证 | 每 50 步对 12 个固定实例贪心解码评估 |

## 8. 基线、局部搜索与动态重规划

### 8.1 两个基线（RV-19）

- **贪心（`solvers.greedy_solve`）**：每步在"可行且剩需求"的 (k,j) 中选 `leg·(1+γ·risk_j)` 最小的（风险邻接 + 少量随机扰动打破平局）。它的意义是"人力能写的启发式天花板参照"。
- **OR-Tools（`solvers.ortools_solve`）**：工业级 MDVRPTW 求解器。因为 CP-SAT 无法直接表达 Σw·t，用**代理代价** `c[i,j]=T[i,j]·(1+γ·w_j)` + 软窗惩罚 + makespan 系数近似，最后仍回统一评分器打分。报告 §8.2-④ 如实标注了这一"代理目标偏差"。

### 8.2 局部搜索精修（RV-20）

NN 构造解是"好种子"但未必局部最优。`evaluate.local_search` 对初解做 ≤800 次"改进即接受"的扰动：线路内 **2-opt**（翻转一段）+ 跨机 **relocate**（把一个节点搬到另一架机的路线），任何使目标下降的改动保留。

> ⚠️ 这里有一个**已实测确认的严重 bug**（§12-①）：改动被拒绝时，代码把当前解重置回了**最初的输入解**而不是"上一次被接受的最好解"。实测后果：它连一次成功改进都保不住，在 16 个测试场景上实际输出与输入完全一致（改进 0.0%）。修掉这行之后，贪心+局部搜索从 37.77 直接降到 **16.87**——与 RL 的 16.69 仅差 1%，且风险加权时间指标（15.60）反超 RL（15.83）。**报告的 §5.2 主表因此严重高估了 RL 的相对优势**（详见质量审查报告）。

### 8.3 推理：采样取最优

训练好的策略单条轨迹是随机的，所以推理时**对同一实例采样 32 条轨迹，用统一评分器挑最好的**（`evaluate.solve_rl`）。报告 §5.3 的敏感性：S=1→8 提升 3.3%，8→32 提升 2.0%，32→128 再提升 0.5%。这是 NCO 的标准操作，也是 POMO 训练与采样推理同构的回报。

### 8.4 事件驱动滚动重规划（`replan_demo.py`，RV-17）

警报是陆续到达的（演示流：t=0 报 5 点 → t=20 再报 2 点 → t=45 再报 3 点）。做法：

1. 每个事件时刻把无人机推进到该时刻（离散事件仿真）；
2. 构造"当前状态 + 所有未完成任务"的子实例；
3. 用策略网络重解 → 新路线整体替换旧计划（`make_replan_instance` 把"每架机当前位置"变成子实例的临时停机坪）；
4. 对照策略：固定波次（不重排）与最近邻即时指派。

报告 §5.4 结果：重规划的"风险加权响应延迟"18.66，比固定波次 25.91 低 28%。直观原因：t=20 到达的高风险点能插进现有计划"同场竞争"，而不是排队等上一波完成。

## 9. 一次完整推理的逐步走查（真实数据）

用真实训练好的模型在 `seed=9000, wind_hour=0`（2024-06-01T00:00，风矢量 u,v = (−1.5, −0.1) m/s）的场景上走一遍。

### 9.1 输入场景（13 节点）

```
节点  角色    x(km)   y(km)  风险w   软窗(min)
 0    停机坪   0.83    3.57   —       —
 1    停机坪  -2.62   -2.95   —       —
 2    停机坪   4.00   -0.52   —       —
 3    任务     0.34   -0.88   0.43    50.6
 4    任务     1.05   -0.48   0.57    44.2
 5    任务     1.92   -0.50   0.93    28.2   ← 最高危
 6    任务     1.44   -2.06   0.23    59.4
 7    任务    -0.69   -0.41   0.18    62.1
 8    任务    -0.82    1.08   0.64    41.1
 9    任务     1.61    0.04   0.97    26.3   ← 最高危
10    任务     0.07    1.45   0.64    41.0
11    任务     1.73    0.52   0.06    67.2   ← 最低危
12    任务    -0.86   -1.41   0.30    56.4
```

风的不对称性实例：T[3,7]=1.45 min（顺风方向）vs T[7,3]=1.73 min（逆风方向），单边差 0.28 min，全矩阵最大不对称 1.90 min。

### 9.2 编码

13 个节点的 6 维特征 → 128 维嵌入 → 3 层 Transformer 编码器（每层：多头自注意力 + 残差 + LayerNorm + FF 512）→ h_0…h_12。整个矩阵一次性算完，随后 32 条采样轨迹复用同一批嵌入。

### 9.3 解码（示意前几步）

第 1 步：三架机都在各自停机坪，载荷满、电量满。解码器为每架机构造查询 q_k，对 13 个节点算 logits（3×13 矩阵），屏蔽不可行项（例如"回站"动作此刻全部被屏蔽——没补给需求）。softmax 采样得到第一个动作。

模型最终（32 条采样里最好的一条）给出：

```python
routes = [[10, 8, 7], [12, 3, 6], [5, 9, 4, 11]]
```

直觉检查：最高危的 5(w=0.93) 和 9(w=0.97) 都在各自路线**第一或第二个**；最低危的 11(w=0.06) 排在最后——模型学会了风险排序。

### 9.4 评分

`env.objective_times` 逐机回放：

```
任务完成时刻 t_j = [5.80  5.52  3.16  8.34  6.72  4.50  4.25  3.15  7.73  3.66] min
各机结束时刻（未含返航）= [12.93, 13.58, 12.11] min
```

代入目标：

```
Σ w·t  = 22.37          （0.97×3.66 + 0.93×3.16 + … —— 高危点几乎全部 ≤ 8 min 内完成）
迟到罚 = 0              （全部在软窗内）
makespan 项 = 0.05×13.58 = 0.68
总目标 Objective = 23.05
```

### 9.5 推理成本

32 条采样、13 节点、CPU：约 0.04 s。这就是"警报到达 → 立刻出新计划"的底气。报告 §8.1-③ 称前向 <5 ms 是指单条轨迹。

## 11. 前提知识速览（零基础补课区）

**VRP 家族**：TSP（一位旅行商走完所有点）→ VRP（多辆车、容量限制）→ VRPTW（加时间窗）→ MDVRP（多车库）→ HFVRP（异型车辆）。本项目是这些的"无人机风险投放"变体：软窗+风险权重、能量含返航、风致非对称成本。

**指针网络 / Attention Model**：解码器不输出"坐标"，而是对"输入节点的嵌入"打分并"指向"其中一个——天然适配输出=节点序列的组合优化问题。

**Transformer 自注意力**：每个节点与所有节点算相关性（QKᵀ），加权聚合价值（V）。对完全图路由问题，注意力 ≈ 全图消息传递。

**REINFORCE**：策略梯度——好轨迹提高概率、坏轨迹降低。**共享基线**：减掉同实例均值，减小方差。

**softmax + 掩码**：`softmax(logits − 1e9·infeasible)` 让不可行动作概率趋近 0，概率之和不变。

**统一评分器**：把"解"（routes）翻译成"一个数字"（Objective）的函数——训练（奖励）、推理（选优）、对比（公平）三方共用。

## 12. 已核实的实现缺陷清单

教学的最后一步是"怎么怀疑"。以下每条都已在本机复现验证（细节与建议修复见 `05_质量审查报告.md`）：

1. **局部搜索是空操作（已实测）**：`evaluate.local_search` 在拒绝一次改动时把解重置回最初输入，而非当前最好解，导致 16 个测试场景上改进 0.0%；修复后贪心+LS 的目标从 37.77 → 16.87，与 RL 16.69 基本持平，报告 §5.2 的"RL 对贪心+LS 优 56%"主结论因此失真（真实约 1%，且 rwt 指标上 LS 反超）。
2. **训练时多机共享一个时钟（已实测）**：`train.rollouts` 的 `time_now` 是每轨迹标量，三架机的飞行时间累加在同一数上（≈ 真实 makespan 的 2.8 倍），策略的"时间"输入与时间掩码被扭曲；最终评分不受影响（`env` 逐机重算）。
3. **OOD 表中"OR-Tools"列其实是贪心（已实测）**：9/9 个 OOD 实例上 OR-Tools 求解失败并静默回退到贪心（`solvers.py` 的 `sol is None → return greedy_solve`），报告表 4 的 OR-Tools 数字与贪心逐行相同却未披露；且 9 行结果只展示了 6 行。
4. **多访问任务的完成时刻取错了统计量**：`env.objective_times` 对 demand>1 的任务用 `min()` 而非"第 demand 次访问时刻"（应为 max），OOD 转换中所有任务 demand≥2，OOD 数值全部被此污染。
5. **λ 敏感性消融为空**：`ablation.py` 的 `lambda_sens` 未实现（结果 JSON 里 0 行），但报告 §8.2-② 引用"灵敏度分析确认鲁棒区间"作为权重手工标定的论据。
6. **复现命令与实际模型不一致**：`train.py` 默认 `--d 96`，正式 checkpoint 是 d=128；README 的复现命令未加 `--d 128`，照抄会训出另一个模型。
7. **仓库卫生**：`data/raw/` 共 2.0 GB 且完全未纳入 git 管理；约 48 MB 逐字节重复目录、547 MB 截断损坏的 `olist_coordinates.zip`（数据文档却称"已验证完整"）、`_work/` 调试残留 2.5 MB。

**结论**：这个模块的**架构设计、文献/数据调研和文档诚实度**是高质量的；但**实验环节的实现缺陷**使报告中的若干关键数值结论不可直接采信。写教学文档的目的正在于此——理解它好在哪里，也知道它坏在哪里，然后修掉坏的。
