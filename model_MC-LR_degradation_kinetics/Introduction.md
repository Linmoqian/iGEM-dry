# MC-LR 降解动力学模型入门

## 1. 它在系统里负责什么

当检测模块发现 MC-LR 风险后，系统不只需要知道“要不要投放”，还需要知道：投放多少工程菌、多久能把毒素降到安全线、什么时候可能需要再次投放。

本项目就是这个反应层：

```text
初始 MC-LR 浓度 C0 + 投放剂量 D + 温度/pH/DO/光照
                         ↓
              MC-LR 随时间如何被降解
                         ↓
      C(t)、达到 1 μg/L 的时间、剂量-时间决策曲线
```

它只描述一个点或一个局部处置单元内的“反应”，不负责：

- 藻华如何生成；
- 整个东湖的二维扩散和漂移；
- 毒理学风险分级。

二维水流模型负责空间输运，本项目提供可以作为反应汇项的降解速率；路径规划模型负责无人机访问顺序。

## 2. 为什么采用“灰箱”而不是纯机器学习

公开的 MC-LR 降解数据有三个问题：

1. 真实工程菌数据很少；
2. 不同菌株、纯酶、整细胞和天然菌群的速率可以相差 3–4 个数量级；
3. 温度、pH、底物浓度、菌量和光控自杀会同时影响速率。

只用机器学习，训练数据不够；只用一个纯机理模型，又没有可信的工程菌参数。因此项目选择灰箱架构：

```text
文献/湿实验数据 ──> 参数先验与校准
                         ↓
机理 ODE 内核 + 环境修正 + 菌/酶动态
                         ↓
蒙特卡洛不确定性传播
                         ↓
剂量-时间反问题和决策卡
```

“灰箱”的意思是：状态变化遵守生物化学和质量守恒的骨架，但速率、环境敏感性和菌株差异用数据估计，而不是假装所有参数都已知。

## 3. 生物学过程：为什么不是一个简单的 `C'=−kC`

工程菌携带的 mlr 通路可以粗略分成级联步骤：

1. **MlrA** 先把环状 MC-LR 在关键位点开环，形成线性化产物；
2. **MlrB** 继续切断中间片段；
3. **MlrC** 将其切成更小的肽段和分子；
4. Adda 转氨酶等模块进一步处理末端产物。

开环后毒性会显著降低，但“原始 MC-LR 消失”和“所有产物都变成无毒小分子”不是同一时刻。因此模型保留 `C`（环状毒素）、`L`（线性化中间体），并在完整架构中预留 `P`、`X` 等后续状态。

还需要描述菌和酶本身：

- `B`：活菌密度，可能生长、死亡或被水流冲刷；
- `E`：活性酶量，受菌量、诱导和降解影响；
- `C_intra`：藻细胞/胞内毒素池，细胞裂解时可能产生反冲峰值；
- `C_ads`：沉积物或颗粒物吸附态，可能先吸附、后释放。

这就是为什么最终架构建议 5–9 个状态，而不是用一个固定 `k` 概括所有情况。

## 4. 机理内核如何计算

完整规格中的主方程可用下面的简化图理解：

```text
C --(MlrA, Michaelis-Menten)--> L --(MlrB/C)--> P --> X
│
├── 胞内释放/背景菌群增加
└── 颗粒吸附/解吸

B(t) ──> E(t) ──> 各级反应速率
```

例如第一步速率写成：

```text
vA = kcat,A × E(t) × C/(Km,A+C) × ψ(T,pH,DO)
```

当环境浓度远低于 `Km` 时，它会近似一级反应；浓度接近或超过 `Km` 时，酶会饱和，继续提高浓度不会等比例提高速率。保留 Michaelis-Menten 形式可以覆盖这两种情况。

代码求解时使用 `scipy.integrate.solve_ivp`，原型配置为 LSODA，并设置自适应步长、较严格的 `rtol/atol`。这样既能处理快的酶促反应，也能处理慢的菌群死亡和环境变化。`C(t)=1 μg/L` 被作为事件，可以直接求达到安全线的时间，而不必只从粗网格上估计。

## 5. 环境修正模块

环境影响以乘性因子进入速率：

```text
ψ(T,pH,DO) = fT(T) × fpH(pH) × fDO(DO)
```

- `fT`：温度偏离菌株适宜范围时，降解变慢；正式架构选择 CTMI 形式，因为它有最低温度和最高温度边界；
- `fpH`：pH 可能在最适值附近最高，酸侧和碱侧宽度可以不同，因此使用非对称高斯；
- `fDO`：溶解氧影响好氧菌的活性；
- 浊度、营养盐和碳源：主要影响背景菌群、吸附和生长/诱导项。

不同菌株的 `Topt`、`pHopt` 等参数不能强行共用。层次贝叶斯校准用“总体先验 + 菌株随机效应”表达这一点：相似菌株可以共享信息，明显不同的株系又不会被平均掉。

光控自杀也是项目特有的约束：自然光可能让工程菌在几小时内失活。模型用 `δ(I)` 描述光照导致的死亡，如果有效窗口短于治理所需时间，就应输出“需要二次投放”或“需要避光载体”的工程建议。

## 6. 文献数据怎样进入模型

`data/raw/` 保存原始论文表格、微宇宙数据、菌株信息和序列；`data/processed/` 保存团队提取/拟合后的表格。主要脚本是：

- `fit_literature.py`：从文献数字化表格检查伪一级关系、拟合温度/pH 形状、整理不同体系的表观 `k`，生成 `fig7_literature_calibration.png` 及参数表；
- `extract_mendeley_mclr.py`：从 Mendeley 工作簿提取 MC-LR 时间序列和 7 天表观速率，标出低于检测限的数据；
- `extract_lake_erie_ratios.py`：计算 Lake Erie 数据中的 MC-LR/总 MC、胞外/总量比例，为 `C_intra` 和分析物换算提供参考。

正式计划使用层次贝叶斯模型：

```text
log(k_i,j) ~ Normal(总体趋势 + 环境/菌株协变量 + 菌株随机效应, σ²)
```

如果本项目湿实验数据仍少于可辨识规模，模型应退化成“文献先验 + 情景灵敏度分析”，并明确标记为没有完成数据校准，而不是强行训练一个参数很多的模型。

## 7. 从浓度曲线变成剂量决策

模型最终要解的是一个反问题：在目标时限内达到 `C_target=1 μg/L`，最少投放多少菌？

```text
D* = 最小化剂量/超时/残留成本
     约束：P(t_safe ≤ T_limit) ≥ 1−α
```

输出不是一个孤立的剂量数字，而是一张决策卡：

- 推荐剂量及允许上限；
- 中位治理时间和 90% 区间；
- 当前温度、pH、DO 带来的减速；
- 是否超过光控存活窗口；
- 是否需要二次投放；
- 哪些参数最影响结果。

剂量-时间等值线图的白色/空白区域也很重要：它表示在给定最大剂量和时间内根本达不到安全线，应升级处置而不是继续盲目增加飞行次数。

## 8. 当前代码实际实现到哪一步

当前目录同时包含“最终架构规格”和“可运行原型”，两者要区分阅读：

### 已可运行的原型

`src/prototype_v1.py` 可以直接生成架构图、通路图、模拟轨迹、剂量-时间等值线和不确定性示意图。它实际使用的是两状态 `C/L` ODE：MlrA 开环 + 合并后的后续一级反应，并用简化的菌量指数衰减、温度高斯函数和 pH 高斯函数演示方向。

`src/fit_literature.py` 可以运行文献表格拟合和图 7 生成，`src/extract_*.py` 可以运行数据提取。

### 尚未完全落地的部分

- 报告 v1.1 规格中的 CTMI 温度函数、非对称 pH 函数、`E(t)`、胞内池和完整级联尚未全部接入 `prototype_v1.py`；
- 层次贝叶斯/HMC 参数校准目前是架构设计和接口规划，不是已经用本项目工程菌数据完成的正式训练；
- 代理模型、完整决策 API 和与二维水流的 operator splitting 尚未形成最终联调版本。

## 9. 重要的科学审查结论

首次阅读时尤其不要把 `fig4–fig6` 的数值当成已经校准的现场预测。质量审查指出：

- 原型使用的 m6 `k≈0.25 h⁻¹` 主要来自论文“整小时完成时间”网格化后的比例，不能直接当作精确动力学常数；
- 温度/pH 拟合点数很少，CTMI 的高 R² 受到“参数数目接近数据点数”的影响，应视为形状假设；
- `prototype_v1.py` 仍使用旧的对称高斯环境函数，和报告 v1.1 的校准规格不完全一致；
- USGS 微宇宙提取并未覆盖所有分离株，天然背景降解速率应以区间/上限先验表达；
- Klebsiella 和 YF1 数据的浓度范围与东湖环境浓度有较大域差异，不能直接外推。

因此当前最准确的结论是：**灰箱架构和数据处理管线已经搭好，文献提取和可运行原型已经完成，但正式工程菌参数和现场剂量数字仍需 v1.2 湿实验重新锚定。**

## 10. 和其他模块怎样连接

| 上游/下游 | 连接内容 |
|---|---|
| 浓度标定 | 提供 `C0` 及其不确定性，而不是只传一个点估计 |
| 风险预测 | 提供是否启动治理、风险斑块和时限 |
| 二维水流 | 用 `−r(C,B,T,pH,...)` 作为网格中的反应汇项；空间平流由水流模块负责 |
| 路径规划 | 使用每个投放点的需求包数、漂移时滞和治理生效时间 |
| Web/控制端 | 展示剂量、达标时间区间、二次投放建议和域外警告 |

`model_path_planning/code/flow_tasks.py` 已经演示了这条接口：用初始浓度、剂量-时间关系生成 `demand`，用漂移时间加安全时间生成 `eff_lag`。但其中仍有演示常数，正式联调前必须替换。
